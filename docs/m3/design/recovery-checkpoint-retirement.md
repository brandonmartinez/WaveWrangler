# Recovery checkpoint retirement: explicit Discard only

**Status:** pre-code proposal for independent review, not implementation or M3 acceptance. Refs #30 #27 #41. This document starts from `main`, not the rejected recovery stack; it addresses the [four blockers in the independent #352 review](https://github.com/brandonmartinez/WaveWrangler/pull/352#issuecomment-6074080981). The user-directed rule here is deliberately stricter than the optional verified-save retirement route recorded on #30: **no save, readback, model equality, file identity, lifecycle event, or copy ever authorizes automatic checkpoint deletion.** Only a separately confirmed, identity-bound **Discard** does. The resulting extra offers and device-local storage are intentional. This supersedes the automatic C2b cleanup wording in [M1 C2b](../../m1/ww-009-m1-contracts.md#c2b--unpublished-edit-checkpoint-record-d); the implementation author must update that contract and the engineering guide when changing behavior.

## What is retained, and what a save proves

- A C2b unpublished whole-model edit checkpoint, whether still in `edit-checkpoints/<key>/` or set aside in `edit-checkpoints-offered/<key>/`, is immutable user-work evidence. Keep **every** validated record across subsequent checkpoints, Save, autosave, Save As, Save a Copy, Revert, Undo/Redo, Don't Save, close/quit, restart, file move/rename/replacement, format update, and provider changes. Moving a record to the offered directory is not retirement. A restore is an undoable *in-memory* edit, not a disposition of its record; saving a restored model does not dispose of it. A record can become copy-only or temporarily unverifiable, but remains available or explicitly reported on reopen.
- Apply the same no-save-driven-deletion rule to coherent C3 prior-revision checkpoints: `RecoveryStore.retainCheckpoint` currently prunes beyond `retainCount` **during Save**. Remove that pruning when implementing this policy, while retaining at least the two-prior minimum and whole-record validation. `verified-current` is a separately replaceable current-state cache, not permission to remove a prior; verify that its predecessor is retained first. Conflict candidates and migration backups remain retained under their existing protections. Only uncommitted staging debris may be cleaned automatically, never a validated recovery record. This changes the old bounded-storage tradeoff: surface device-local storage use and offer individually confirmed Discard for older records; do not silently age out or impose a hidden cap. If the required prior cannot be retained because storage is full, refuse publication *before* the canonical write and report the error.
- A successful native save means an encoded candidate was validated, a permissible base checked, stock AppKit safe-write returned, and an independent readback at the target matched **that candidate's entire encoded envelope and publication** at verification time. It does not prove that a moved old file is the new object, that a provider cannot subsequently replace the file, that the C2b snapshot bytes equal the new save bytes, or that a provider has synced another device. The restored model can match a checkpoint while a normal save creates a fresh `publicationID` and different envelope bytes (`ShowDocument.swift:246-248`, `DocumentPublisher.swift:258-270`). Neither model nor byte equality is needed for retirement because there is **no automatic retirement**.
- Preserve the M1 source/durability guards: refuse newer/read-only formats, keep a validated prior before overwriting, detect an observable base conflict, never overwrite known competing work, and never claim a failed/unverified publication was saved. `NSFileCoordinator` and `AlreadyCoordinated` narrow cooperating access; neither is an exclusive provider CAS (`FileCoordination.swift:3-8,80-85`). This proposal removes the *retirement* need for an old-object-to-new-object receipt and readback-to-delete atomicity; it does not pretend to solve provider identity or guarantee continuously current disk truth.

## Feasible native failure boundary (independent of retirement)

The installed macOS 27 `AppKit.framework/Headers/NSDocument.h` (SDK `MacOSX27.0.sdk`, lines 288-302, 394-400, 683-691) describes the order: the default `saveToURL:...completionHandler:` calls `writeSafelyToURL:...`; **only if that returns success** does it update file URL/type/modification date and change count, before calling completion. The safe-write itself may rename the old file, write a temporary one and move it into place; its internal steps vary by filesystem. Returning a new error only from the *outer completion* or `finishSave` is too late to prevent AppKit from clearing the edited token or adopting a Save As URL. Do not use that strategy.

Use the supported existing seam: `ShowDocument.canAsynchronouslyWrite(...) == false` (`ShowDocument.swift:142-147`), and `ShowDocument.writeSafely(to:ofType:for:)` (`:570-603`) invokes `DocumentPublisher.publish(encoded:..., step: .external)` with `AlreadyCoordinated`. The external step calls `super.writeSafely`, after which the publisher independently reads the final target and checks exact candidate bytes plus decoded publication **before `writeSafely` returns** (`DocumentPublisher.swift:291-389`, especially `:345-382`). Failed, unreadable or mismatched readback throws `PublicationError.acknowledgementUncertain` from this override; an invalid candidate, base conflict or write failure also throws here. `super.save` therefore receives a failed safe-write and must call its completion with a **non-nil error**. Propagate that same error to native Save/Close/Quit and custom copy handling; never convert it to `completionHandler(nil)`, never set `.saved`, and never call `.changeCleared` on that path. Pin this ordering with a native injected post-write/readback failure test that observes `isDocumentEdited`, `fileURL`, the completion error, and the close decision, rather than assuming an error thrown from a late callback can fix the token.

Capture each save's model, encoded bytes, target, operation, key and generation in one per-attempt context before calling `super.save`; refuse/serialize a second save while it owns `pendingCandidate`/`lastReceipt` so `data(ofType:)` cannot supply another attempt's bytes. At the safe-write boundary, verify the matching context and candidate are still bound; do not let an empty/overwritten receipt turn into a success-shaped outer callback. For an already-dirty document (including Restore), AppKit's success-only token update has not run when verification throws, so it stays dirty. For an explicit save that began clean but nonetheless writes and fails verification, explicitly mark it edited (or keep an equivalent AppKit change token pending) before reporting the error: the requested failure state must be dirty even in that case. Later retries may independently verify and acknowledge what landed; they must not retire checkpoints. Keep the existing success-only autosave-in-place `.changeCleared` behavior for the verified-current model (`ShowDocument.swift:318-330`); it must not execute on failure.

**Failure is not rollback.** Once `super.writeSafely` has returned, the candidate may already be at the target even if readback then fails or sees another value. Return a non-nil *verification/acknowledgement-uncertain* error, keep the document dirty and its checkpoints, and say “The save may have written the file, but WaveWrangler could not verify it. Your recovery copies are still on this Mac. Reopen or compare before trying again.” Do **not** say “the old file is unchanged,” rewrite over an uncertain base, mark the library acknowledged, permit a success-driven close, or classify it as a known pre-write failure. Before publication, an offline/read-only/denied or changed-base refusal leaves the candidate in memory and the checkpoint in storage and gives the corresponding non-nil error; retry/regrant or Save a Copy is the way forward. A successful Save As or Save a Copy can mark its **destination** saved, but it says nothing about the original and never retires its record.

File identity is a separate, bounded pre-write safety check, not a deletion receipt. At open, associate the document's origin URL/key with whatever trustworthy per-volume file identity is actually available; immediately before an origin-targeted overwrite, compare the current resolved item with that observed identity **and** independently check the expected canonical base. A moved original plus a byte-identical replacement at its old path must be refused as an origin conflict if identity changed. Where identity is missing/unstable (including a provider that cannot reliably supply it), do not certify an *origin-targeted overwrite*: refuse it before the stock write with a visible identity-unknown error and offer a separate destination/reopen path. A first save to a verified empty new location is not an origin overwrite and does not need an old-file identity. A successful AppKit atomic safe-save may legitimately change the final object's ID, so do **not** compare old and new inode IDs to claim identity continuity. After safe-write, the exact readback certifies bytes **at the target at that instant**, not which pre-write object became it. If a provider replaces it after readback, there is no general exclusion/CAS to certify ongoing identity; keep the checkpoint, respond to observed change as a conflict/recheck, and do not assert that the moved original was saved. If a future requirement demands post-write identity-continuity certification rather than target-byte verification, this seam alone cannot provide it: that requires a provider-specific transaction witness or an explicitly approved different save protocol, not a path/byte heuristic.

## Only retirement transaction

The offer must remain visible and reachable after Restore and after save; `restoredOfferURLs` is a transient undo/display mark, **not** a deletion entitlement. After a save, a record whose validated decoded content appears to match the saved model may say “A recovery copy is still kept on this Mac; its content appears to match this saved version. Review it or choose Discard to remove this copy.” Do not promise identical file identity or use the old “never saved” wording as an assertion that the current model is still unpublished. On failed/unknown reads, say “Could not check whether this recovery copy matches; it has been kept,” with an accessible retry/open-as-copy and Discard only where safe. Older-base and competing-session records stay copy-only; unknown bases never authorize in-place restore. The message-bar heading, body, buttons, AX role/label/value, announcement, keyboard focus, visible focus and confirmation (Cancel/Escape, no destructive default) must work in native windows, including the state-restoration display path.

On **user-confirmed Discard of one displayed record**, capture `(record kind, DocumentKey, unique immutable record URL/ID, digest of the full stored record)` when offering/confirming it. Re-read that exact app-owned record under one recovery-store serialization boundary, validate its kind, logical key, digest and current identity; if it changed, disappeared unexpectedly or cannot be read, report a non-nil failure, refresh the offer and remove **nothing else**. Only then remove that selected physical record, confirm deletion actually succeeded, invalidate that record's restore/Undo-Redo mark, and expose the next offer. No bulk key-wide cleanup behind a Discard button. Use unique, never-reused names and one app-owned lock/serialized store mutation for all cooperating processes so a new record cannot replace the selected path between identity check and deletion; untrusted external tampering is not a provider transaction. If those ownership conditions cannot be established, refuse Discard instead of deleting by a stale URL. Keep the confirmation specifically about that record (and display revision/time or other non-sensitive identity); Cancel or a failed remove does not clear the offer. An unusable/damaged record needs a separately explicit, identity-bound Discard route rather than silent cleanup.

Remove or restrict **every non-Discard delete** in the implementation: `ShowDocument.finishSave`'s `try? discardEditCheckpoints`, `resolveOfferRecordsAfterVerifiedSave`, `saveCopy`'s original-key cleanup, `adoptUncertainPublication` cleanup, and `close()`'s Don't Save/restored-offer cleanup (`ShowDocument.swift:333-337,460-468,552-561,770-813`); `CanonicalDocumentSession.save`/`discardUnsavedChanges` (`:138-139,214-216`); `RecoveryStore.writeEditCheckpoint`'s old-draft pruning and `retainCheckpoint`'s C3 pruning (`RecoveryStore.swift:46-57,193-222`). Append new drafts using a sequence/unique ID reserved across **active and offered** records under that same store serialization boundary: the current sequence derives only from active files and can reset after set-aside. Never replace an earlier record to make space. A saved separate copy must release its temporary *display suppression* and reoffer the original record, not delete it. Revert/reload invalidates transient restore marks and stale undo callbacks but retains every physical record. An explicit native **Don't Save is not the separately confirmed Discard**: the window may close, while recovery remains available on reopening; update stale close/recovery wording accordingly. Update existing unit tests that currently assert automatic deletion, not just add new ones. Replace ignored `try?` on remaining Discard with surfaced failure and an observed absence check; do not silently treat “not found” as successful deletion or conflate a status/offer refresh with physical removal. Also surface failed draft creation (`ShowDocument.writeEditCheckpoint` currently uses `try?`) instead of implying the edit was checkpointed.
